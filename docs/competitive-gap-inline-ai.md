## 0. 한 줄 결론

HOP은 **"HWP를 정확하게 고치는 엔진"으로는 이미 경쟁력이 있지만, "내 컴퓨터 속 AI 비서"라는 제품 범주에는 아직 들어가 있지 않다.**

격차의 대부분은 AI 품질이 아니라 **접점(Windows 미배포)·범위(파일 1개/포맷 1개)·진입장벽(API 키)** 에 있다. 셋 다 모델을 더 잘 쓰는 문제가 아니라 제품 결정 문제다.

## 1. 비교 기준 정리

inline AI가 공개적으로 내세우는 것:

| 항목 | inline AI 주장 |
|---|---|
| 정체성 | "내 컴퓨터 속의 AI 비서" — 로컬 파일을 직접 편집 |
| 핵심 차별점 | "여러 파일을 동시에 편집하는 최초의 로컬 AI 에이전트" |
| 강점 지표 | SpreadsheetBench 1위, Excel 정확도 92% |
| 포맷 | Excel, 한글, PDF, 이미지, Word, PowerPoint |
| 사용자 | 12.6만 명 (회계·재무·기획·연구·법률·교육) |
| 보안 | 100% 로컬 처리, Anthropic/OpenAI와 ZDR 계약 |
| 배포 | Windows (v0.4.4) |
| 과금 | 크레딧제 — 무료 1,000 / Pro 29,900원 5,000 / Team 60만원~ / Enterprise |

주의: 위는 **자사 마케팅 문구**다. "최초", "1위", "12.6만"은 검증하지 않았다. 다만 *경쟁 기준선*으로는 그대로 쓰는 게 맞다 — 사용자가 비교하는 대상이 저 문구이기 때문이다.

무료 티어가 **월 1,000 크레딧**이라는 점은 중요하다. HOP이 노릴 자리는 "유료보다 싸다"가 아니라 **"크레딧이라는 개념 자체가 없다"** 이다.

## 3. 결정적 격차 — 심각도 순

### G1. Windows에 없다 · **치명적**

타깃 사용자(공무원·회계·연구행정)는 사실상 전원 Windows다. 한글 문서를 다루는 사람 중 macOS 비중은 무시할 수 있는 수준이다.

지금 상태는 **"기능이 부족하다"가 아니라 "사용자가 실행조차 할 수 없다"** 이다. 아래 G2~G8을 전부 구현해도 이게 안 풀리면 사용자 수는 0에 수렴한다.

- 현실: CI에 `windows_x64` 잡이 **이미 배선돼 있다**(`hop-desktop.yml:145`). 켜지지 않았을 뿐이다.
- 남은 실제 일: Windows 빌드 통과 확인, 코드 서명(미서명 exe는 SmartScreen 경고 → 공무원 PC에서 사실상 차단), 릴리스 게이트의 macOS 강제 조건 완화, 웹사이트/README 다운로드 링크 추가.
- 비용 추정: 서명 인증서(연 20~40만원)가 유일한 실비. 나머지는 엔지니어링.

> **이게 P0다. 다른 어떤 항목보다 먼저다.**

### G2. API 키 장벽 — "무료"의 진짜 난제 · **치명적**

여기가 이 프로젝트의 핵심 모순이다.

- inline AI 무료 티어: **가입 → 즉시 사용** (월 1,000 크레딧)
- HOP: **Anthropic 콘솔 가입 → 결제수단 등록 → 키 발급 → 앱에 붙여넣기**

BYO-key는 *비용*은 무료로 만들지만 *진입장벽*은 inline AI보다 훨씬 높다. 회계 담당 공무원에게 "Anthropic API 키를 발급받으세요"는 사실상 거부다. **"무료로 만들어주려 했다"는 의도가 이 지점에서 좌초한다.**

선택지는 셋이고, 각각 성격이 다르다:

| 안 | 내용 | 장점 | 대가 |
|---|---|---|---|
| **A. 호스팅 무료 티어** | HOP이 게이트웨이를 운영, 일 N회 무료 | inline AI와 동일한 무마찰 온보딩 | 실서버 비용 발생 → "무료"가 아니라 "내가 부담" |
| **B. 로컬 모델 번들** | ollama + 소형 한국어 모델 동봉 | 진짜 무료·완전 오프라인·ZDR 불필요 | 소형 모델로 HWP ActionScript 정확도가 나오는지 **미검증**. 다운로드 용량 수 GB |
| **C. 키 입력 UX를 극한으로 단순화** | 발급 화면 딥링크 + 붙여넣기 검증 + 잔액 표시 | 비용 0, 구현 작음 | 장벽이 낮아질 뿐 사라지지 않음 |

권고: **C를 즉시 하고, B를 검증하고, A는 마지막에.** B가 되면 HOP은 inline AI가 구조적으로 따라올 수 없는 자리(오프라인·무제한·무비용)를 갖는다. B의 성패는 **소형 모델이 ActionScript JSON 스키마를 안정적으로 뱉는가** 하나에 달렸고, 이건 하루면 실측할 수 있다. **먼저 측정할 것.**

### G3. 파일 1개만 다룬다 · **높음**

inline AI의 1번 마케팅 문구가 "여러 파일 동시 편집"이다. 그리고 **HOP은 이미 엔진을 갖고 있다** — `docx-batch-convert.batch.ts`가 GUI 없이 rhwp WASM으로 12개월치 연구노트를 일괄 변환한다.

즉 이건 신규 개발이 아니라 **노출 문제**다. 파일/폴더 선택 UI + 진행률 + 파일별 성공/실패 리포트를 붙이면 마케팅 문구가 대등해진다. 투자 대비 효과가 가장 큰 항목.

주의: 지금 배치 도구는 `BATCH_FORM`/`BATCH_DOCX_DIR` 환경변수 + vitest 실행이 전제다. 사용자 노출용으로 올리려면 Tauri 커맨드로 승격하고 실패 격리(1개 실패가 전체를 중단시키지 않게)를 넣어야 한다.

### G4. Excel이 없다 · **높음 — 단, 정면 대응은 권하지 않음**

inline AI가 가장 강하다고 주장하는 영역이고, 실무 수요도 한글보다 크면 컸지 작지 않다. 하지만:

- SpreadsheetBench 92%를 따라잡는 건 rhwp급 엔진을 하나 더 만드는 일이다.
- HOP의 자산(rhwp, 결정적 양식 변환, 스펙 게이트)이 **전혀 전이되지 않는다.**

권고: **전면전 대신 "HWP 1위"에 집중.** Excel은 다음 순서로만 접근한다.
1. **읽기 전용 xlsx** (표 데이터를 HWP 표/차트로 가져오기) — 기존 F-d0dce3 차트 삽입과 직결, 비용 작음
2. 쓰기는 수요가 증명된 뒤에

이건 격차를 인정하고 **의도적으로 포기하는** 결정이다. 문서에 남기는 이유는, 나중에 "왜 Excel 안 했나"가 다시 올라올 때 근거를 남기기 위해서다.

### G5. 에이전트 루프가 없다 · **중간**

HOP은 "요청 → 편집안 1회 → 승인"이다. inline AI가 파는 건 "수백 개 파일을 훑고 정리해준다"는 **자율성**이다. G3(배치 UI)이 이 격차의 80%를 메운다 — 완전한 자율 루프까지 갈 필요는 없고, 오히려 문서 편집에서는 예측 가능성이 더 중요하다.

### G6. 웹 리서치 없음 · **중간**

"로컬 파일 + 웹 리서치"가 inline AI의 무료 티어 문구에 들어가 있다. 구현 난도는 낮다(검색 API 1개 + 인용). 다만 로컬 전용이라는 HOP의 보안 서사와 충돌하므로 **명시적 opt-in**이어야 한다.

### G7. 메모리 없음 · **중간**

inline AI는 Pro 티어 기능으로 판다("업무 패턴·서식 기억"). HOP에는 `conversation-store.ts`(이력)만 있다. 실제로 필요한 건 **문서 서식 프로파일**(이 기관은 표 머리글이 회색, 날짜는 `2026.01.05` 형식) 학습이고, HOP의 결정적 양식 파이프라인과 잘 맞는다.

### G8. 외부 신뢰 신호가 없다 · **중간, 그러나 저비용**

inline AI는 "SpreadsheetBench 1위 92%"라는 **숫자 하나**로 신뢰를 산다. HOP은 28개 feature가 스펙 게이트를 통과했지만 이건 내부 언어다.

HOP이 낼 수 있는 대응 숫자:
- **한글 문서 왕복 무결성**: N개 실제 HWP를 열고 저장해 바이트/렌더 동등성 (rhwp가 이미 baseline 테스트 보유)
- **양식 변환 정확도**: 연구노트 N건 변환 후 셀 단위 일치율
- 한컴오피스에서 열었을 때 깨지지 않는 비율

숫자를 만드는 비용은 낮고, 오픈소스라 검증 가능하다는 점이 inline AI보다 강한 주장이 된다.

## 4. HOP이 이미 이긴 것 — 무료 전략의 근거

격차만 나열하면 방향을 잘못 잡는다. 아래는 **inline AI가 구조적으로 따라오기 어려운** 것들이다.

1. **크레딧 개념이 없다.** BYO-key 또는 로컬 모델이므로 사용량 제한이 원리적으로 없다. inline AI 무료 1,000 크레딧과 비교했을 때 "무제한"은 강력한 문구다.
2. **완전 오프라인 가능.** ollama/openai-compat 경로는 네트워크가 끊긴 망분리 환경에서도 돈다. 공공기관·법률·의료에서 이건 ZDR 계약보다 강한 보장이다. inline AI는 "100% 로컬 처리"라고 하지만 **추론은 Anthropic/OpenAI로 나간다**(그래서 ZDR 계약을 언급한다). HOP은 추론까지 로컬로 만들 수 있다.
3. **HWP 엔진을 직접 소유한다.** rhwp는 자체 파서/직렬화기다. 한컴 설치나 COM 자동화에 의존하지 않는다. 한글 포맷 관련 버그를 스스로 고칠 수 있다.
4. **편집 단위별 수락/거절.** inline AI는 "작업 승인"이고 HOP은 "변경 블록별 ✓/✗"다. 문서 작업에서 이건 실질적 우위다.
5. **표 구조를 LLM에 맡기지 않는다.** 앱이 원본 표를 결정적으로 복제하고 AI는 내용만 채운다(F-ae778890, F-220afd). 실측으로 얻은 설계다 — compose 방식은 6×3 표를 6×2로 망가뜨렸다. LLM 기반 경쟁자가 흔히 겪는 실패를 구조적으로 회피한다.
6. **오픈소스 + 스펙 앵커드 게이트.** 회귀가 게이트에서 잡히고, 사용자가 코드를 검증할 수 있다.

**전략 요약: "inline AI보다 싼 제품"이 아니라 "크레딧도 서버도 없는, 한글에 특화된 오픈소스 로컬 에이전트"로 포지셔닝한다.** 무료가 마케팅 수단이 아니라 아키텍처의 결과여야 한다.

## 5. 로드맵 제안

각 단계는 CLAUDE.md 피처 사이클(shard → 구현 → 테스트 → `clad done`)을 그대로 따른다. 여기서는 **순서와 근거만** 정한다.

### P0 — 접점 확보 (이게 없으면 나머지가 무의미)
